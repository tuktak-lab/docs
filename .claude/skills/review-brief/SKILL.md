# Review Brief

팀원이 발견한 문제를 **수정을 맡을 사람이 빠르게 알아볼 수 있는 형태**로 재배치한다. 정보를 보태는 것이 아니라 배치를 바꾸고 확실성 수준을 표시하는 것이 이 스킬의 일이다.

자연어 리뷰가 읽기 어려운 이유는 두 가지다.

1. **불일치가 산문으로 서술돼 있다.** 세 문서의 내용을 머릿속에 동시에 띄워 비교해야 한다. 표로 나란히 놓으면 바로 보인다.
2. **결론과 추측이 섞여 있다.** "아마 결정이 반영 안 된 것 같은데"는 확인된 사실이 아니다.

## 워크플로우

### 1단계: 이슈 단위로 나누기

**원인이 다르면 다른 이슈**다. 같은 결정이 일부 문서에만 반영돼 여러 곳이 어긋난 것은 이슈 1개(영향 문서 여러 개)로 묶는다. 이슈가 하나면 번호를 매기지 않는다.

### 2단계: 실제 문서로 근거 확인

리뷰어가 지목한 파일을 직접 열어 대조한다. 확인한 내용은 `파일 + 장/요구사항 ID/줄`로 적는다.

- 리뷰어가 언급하지 않은 문서(파생 문서 `docs/*.md`, `README.md` 포함)도 같은 불일치가 있는지 본다.
- 이 저장소의 기준 순서로 판단한다: ① `결정체크리스트.md`의 최신 결정 → ② `요구사항명세서.md` → ③ `기획서.md` → ④ `docs/` 파생 문서. 같은 항목이 나중 날짜로 다시 결정됐으면 나중 것이 기준이다.
- 결정이 `미정` · `보류`이면 기준이 아니다.
- 파일을 열 수 없으면 확인하지 않았다고 적는다. 확인한 것처럼 쓰지 않는다.

### 3단계: 확실성 수준으로 나누기

| 표시 | 의미 |
| --- | --- |
| **확인됨** | 실제 문서를 열어 대조한 사실 |
| **리뷰어 주장** | 리뷰어가 단정했지만 아직 확인 안 됨 |
| **추측** | 리뷰어가 "아마", "~같은데"로 말한 부분 |

### 4단계: 결정이 필요한 지점 분리

- **기준으로 답이 정해지면**(결정체크리스트에 결정이 있거나, 명세서가 정한 값이면) 수정 작업이다. 근거 항목 번호를 적는다.
- **기준으로 답이 정해지지 않으면** 의사결정이다. 어느 쪽이 맞는지 고르지 말고 선택지와 누가 정해야 하는지 적는다. 결정체크리스트에 새 항목이 필요해 보이면 "결정 항목 추가 후보"로만 적는다. 직접 추가하지 않는다.
- 법 조항이 걸린 지적은 팀 결정(D 묶음)과 법적 사실을 나눠 적고, 법 해석을 확정하지 않는다.

### 5단계: 위임용 지시문

결정이 끝난 부분만 doc-editor에게 넘길 지시문으로 만든다. 미결정 항목은 "결정 후 추가"로 표시한다.

## 출력 템플릿

이슈가 하나일 때 기본형이다. 여러 개면 `## 이슈 1`, `## 이슈 2`로 감싸고, 5개 이상이면 맨 위에 이슈 목록을 먼저 둔다. 필요 없는 섹션은 지운다.

````markdown
## 한 줄로

[문제의 핵심과 원인을 한 문장에]

## 무엇이 어긋났나

| 문서 | 뭐라고 되어 있나 | 상태 |
| --- | --- | --- |
| `결정체크리스트.md` (C15) | … | 기준 |
| `기획서.md` (9장) | … | 옛 내용 |

**원인:** …

## 이대로 두면

[구현할 때 실제로 벌어질 일. 한두 줄]

## 확실성

- **확인됨:** …
- **리뷰어 주장(미확인):** …
- **추측:** …

## 먼저 정할 것

- [ ] … — 누가 정하는지

## doc-editor에게 넘길 지시문

```
[복사해서 바로 쓸 수 있는 지시]
```
````

## 지켜야 할 것

- **원문에 없는 내용을 만들지 않는다.** 리뷰어가 "좀 이상한데요"라고만 썼으면 문서를 직접 확인해 채우거나 `확인 필요`로 남긴다.
- **짧게 만드는 게 목적이 아니다.** 지적을 빠뜨리면 실패다. 표가 길어져도 읽는 시간이 줄면 그게 맞다.
- **용어를 풀어 쓴다.** 원문의 기술 용어에는 짧은 괄호 설명을 붙인다. 서비스 용어는 doc-editor 「용어」 표를 따른다 (예: "직원 계정"이 아니라 "매장 계정").
- **리뷰어를 평가하지 않는다.** 지적이 사실과 다르면 "확인 결과 현재 문서에는 이미 반영되어 있음"처럼 사실만 적는다.

## 예시

아래는 형식을 보여주기 위한 **가상의 예시**다. 실제 문서 상태와 다를 수 있다.

**입력:**
> 기획서 보다가 이탈 신호 기간 상한이 90일로 적힌 데를 봤는데 명세서 FR-SET-03은 120일이에요. 둘 중 뭐가 맞는지 모르겠고, 아마 ARCHITECTURE 문서에도 숫자가 있을 것 같아요.

**출력:**

````markdown
## 한 줄로

이탈 신호 기간 상한을 120일로 정한 결정(C15)이 기획서 한 곳에 반영되지 않았습니다.

## 무엇이 어긋났나

| 문서 | 뭐라고 되어 있나 | 상태 |
| --- | --- | --- |
| `결정체크리스트.md` (C15) | 상한 기본 120일, 매장 변경 가능 | 기준 |
| `요구사항명세서.md` (FR-SET-03) | 120일 | 맞음 |
| `기획서.md` (9장 「상태 분류」) | 90일 | 옛 내용 |
| `docs/ARCHITECTURE.md` | 숫자 없음 (명세서 ID만 참조) | 해당 없음 |

## 확실성

- **확인됨:** 위 표 네 곳 모두 파일 대조 완료. 기준은 C15 결정이라 따로 정할 것 없음
- **추측(리뷰어):** ARCHITECTURE에도 숫자가 있을 것 → 확인 결과 없음

## doc-editor에게 넘길 지시문

```
결정체크리스트 C15(이탈 신호 기간 상한 기본 120일)에 맞춰 기획서 9장 「상태 분류」의 90일을 120일로 고쳐 주세요.
고친 뒤 다른 문서에 90일이 남았는지 확인하고 보고 형식대로 알려 주세요.
```
````
